# Internationalization

The web application supports English (`en`), Gujarati (`gu`), and Hindi (`hi`) through `i18next` and `react-i18next`.

## Runtime and persistence

`src/i18n/index.js` initializes translations before React renders. Language resolution is account preference, local storage (`ksm_language`), supported browser language, then English. Changing language updates `document.documentElement.lang` without navigation or component remounting. Authenticated changes are also saved through `PATCH /api/account/preferences/language`; a failed preference sync never blocks the local UI change.

## Translation resources

Resources live below `src/i18n/locales/{en,gu,hi}`. Keys are semantic rather than English sentences. Add the English source first, then natural Gujarati and Hindi equivalents. `src/i18n/i18n.test.jsx` fails when a Gujarati or Hindi key is absent.

## Canonical data rule

Database and API enums remain canonical English values. Components translate display labels with helpers from `src/utils/translatedLabels.js`. User-generated content—including profile descriptions, education details, family details, support messages, and internal notes—is displayed exactly as entered and is never machine translated.

## Dates, numbers, and money

Use `formatDate`, `formatNumber`, and `formatCurrency` from `src/utils/formatters.js`. They map languages to `en-IN`, `gu-IN`, and `hi-IN`. Do not add new hard-coded `en-IN` formatting in UI components.

## Errors and notifications

`ApiError` supports stable `code` values while retaining the existing English `message` fallback. The frontend translates a known code and falls back to the server message for backward compatibility. New stored notifications should prefer a translation key plus parameters; legacy notification text remains untouched.

## Fonts

English uses Manrope and Cormorant Garamond. Gujarati uses Noto Sans/Serif Gujarati; Hindi uses Noto Sans/Serif Devanagari. Font selection follows the `html[lang]` attribute.

## Legal warning

Gujarati and Hindi legal copy requires professional legal approval before launch. All languages correspond to the same semantic `LEGAL_VERSION`; translating a page must not create a separate acceptance version.

## Future multilingual SEO

The SPA currently keeps stable route paths and updates document language. A later SEO phase can introduce localized canonical URLs and `hreflang` (for example `/gu/about` and `/hi/about`) after routing and indexing requirements are approved.
